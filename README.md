# Лабораторные работы по безопасности PostgreSQL

Пошаговое руководство к четырём лабораторным работам и расчётно-графическому заданию (РГЗ). Все примеры рассчитаны на локально установленную **PostgreSQL 18.6** — актуальную стабильную ветвь на 24 сентября 2026 года. PostgreSQL 19 Beta для выполнения работ не используется.

> Учебная предметная область: корпоративная система управления проектами и задачами. Ось сегментации — филиал организации. Пример можно адаптировать к своему варианту, сохранив роли, схемы, правила доступа и последовательность выполнения.

Руководство построено как один последовательный проект. Каждый следующий раздел использует объекты, созданные в предыдущих разделах.

## Быстрый старт

### 1. Установите PostgreSQL локально

Используйте стабильную ветвь 18.x и установите последний доступный минорный выпуск.

- Windows: [официальная страница загрузки](https://www.postgresql.org/download/windows/). Инсталлятор обычно включает сервер, `psql` и pgAdmin.
- Ubuntu/Debian: [официальный репозиторий PGDG](https://www.postgresql.org/download/linux/ubuntu/).
- macOS: [официальные варианты установки](https://www.postgresql.org/download/macosx/).
- Сведения о поддерживаемых версиях: [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/).

Проверьте установку:

```console
psql --version
```

Ожидается строка вида:

```text
psql (PostgreSQL) 18.6
```

Если номер минорной версии новее 18.6, но основная версия равна 18, используйте её: минорные выпуски PostgreSQL совместимы в пределах одной основной ветви и содержат исправления ошибок и уязвимостей.

### 2. Создайте учебную базу

Подключитесь как локальный администратор PostgreSQL:

```console
psql -U postgres -d postgres
```

Выполните:

```sql
CREATE DATABASE security_lab
    WITH ENCODING = 'UTF8'
         TEMPLATE = template0;

\connect security_lab

SELECT version();
SELECT current_database(), current_user, session_user;
```

Для Windows, если `psql` не находится в `PATH`, запустите **SQL Shell (psql)** из меню PostgreSQL либо укажите полный путь, например:

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -U postgres -d postgres
```

### 3. Настройте безопасный режим psql

В начале каждого административного сценария рекомендуется включать остановку при первой ошибке:

```sql
\set ON_ERROR_STOP on
\pset pager off
\timing on
```

Ключ `-X` запрещает загрузку пользовательского `psqlrc`, что повышает воспроизводимость:

```console
psql -X -v ON_ERROR_STOP=1 -U postgres -d security_lab
```

### 4. Выполняйте части последовательно

```text
ЛР № 1 → ЛР № 2 → ЛР № 3 → ЛР № 4 → JIT-раздел РГЗ
```

После каждого смыслового блока сохраняйте SQL в отдельный сценарий. Рекомендуемая структура локального репозитория:

```text
postgresql-security-labs/
├── README.md
├── docs/
│   ├── 01-lab-1-design-and-rbac.md
│   ├── 02-lab-2-security-definer-and-tests.md
│   ├── 03-lab-3-rls.md
│   └── 04-lab-4-audit-performance-and-jit.md
├── sql/
│   ├── 00-bootstrap.sql
│   ├── 01-schema-and-rbac.sql
│   ├── 02-functions-and-tests.sql
│   ├── 03-rls.sql
│   ├── 04-views-audit-performance.sql
│   ├── 05-jit-access.sql
│   └── init.sql
├── tests/
│   └── access-tests.sql
└── diagrams/
    ├── er-diagram.png
    ├── roles.png
    └── rls-flow.png
```

Файл `sql/init.sql` может подключать остальные сценарии:

```sql
\set ON_ERROR_STOP on
\ir 00-bootstrap.sql
\ir 01-schema-and-rbac.sql
\ir 02-functions-and-tests.sql
\ir 03-rls.sql
\ir 04-views-audit-performance.sql
\ir 05-jit-access.sql
```

Команда воспроизводимого развёртывания:

```console
psql -X -v ON_ERROR_STOP=1 -U postgres -d security_lab -f sql/init.sql
```

# Исходное задание

Ниже приведено структурированное содержание методических указаний. Формулировки сохранены по смыслу, а обозначения SQL приведены к единому стилю.

## Лабораторная работа № 1. Проектирование базы данных и классификация данных

**Цель:** спроектировать доменную схему, классифицировать данные и настроить доступ с разделением обязанностей.

### 1. ER-модель и классификация

- Сформировать ER-диаграмму предметной области с ключами и связями.
- Классифицировать данные по уровням `Public`, `Internal`, `Confidential`, `Restricted`.
- Учитывать персональные, финансовые и иные чувствительные сведения.
- Сформировать матрицу «колонка → класс данных».

### 2. DDL и схемы

- Создать схемы `app`, `ref`, `audit`, `stg`.
- Реализовать первичные и внешние ключи, `UNIQUE`, `CHECK`, `NOT NULL` и необходимые индексы.
- Сгенерировать не менее 10 строк в ключевых таблицах.

### 3. Роли и привилегии

- Создать роли `app_reader`, `app_writer`, `app_owner`, `auditor`.
- Создать роли разделения обязанностей: `ddl_admin`, `dml_admin`, `security_admin`.
- Назначить привилегии на уровне схем, таблиц и последовательностей.
- Настроить `ALTER DEFAULT PRIVILEGES`.
- Запретить неявный доступ роли `PUBLIC`.
- Разрешить чтение схемы `audit` только роли `auditor`.
- Запись в `audit` выполнять только доверенными триггерами и функциями.
- Подготовить позитивные и негативные проверки полномочий.

### 4. Логирование подключений

- Создать таблицу `audit.login_log` с полями времени входа, имени пользователя и IP-адреса клиента.
- Реализовать запись сведений о входе с помощью login event trigger PostgreSQL либо документированного сеансового механизма.
- Проверить подключение под разными ролями.

**В отчёт:** ER-диаграмма, матрица классификации, DDL, ограничения, роли, привилегии, тесты доступа и журнал подключений.

## Лабораторная работа № 2. Точечное повышение привилегий и контроль бизнес-логики

**Цель:** реализовать безопасные операции через функции с повышенными привилегиями и сравнить методы контроля бизнес-правил.

### 1. SECURITY DEFINER-функции

- Реализовать 2–3 функции для чувствительных операций предметной области.
- Использовать `SECURITY DEFINER`.
- Выполнять проверку входных параметров.
- Возвращать понятные сообщения о результатах и ошибках.
- Вызывать функции из-под ролей с ограниченными полномочиями.

### 2. Тесты прав

Подготовить не менее восьми позитивных и негативных случаев, включая:

- чтение разрешённых таблиц;
- попытку выполнения DDL неадминистратором;
- прямой DML в `audit`;
- вызов `SECURITY DEFINER` с корректными и некорректными данными.

Тесты допускается реализовать как `psql`-сценарии или с помощью pgTAP.

### 3. Сравнение CHECK и триггера

- Выбрать бизнес-правило.
- Реализовать сопоставимые варианты через `CHECK` и триггер.
- Сравнить корректность, удобство аудита и производительность при вставке 10 000 строк.
- Обосновать выбранный вариант.

### 4. Журнал вызовов функций

- Создать `audit.function_calls`.
- Фиксировать время, функцию, вызывающую роль, безопасно представленные параметры и результат.
- Показать журнал после успешных и неуспешных вызовов.

**В отчёт:** код функций, тесты, результаты сравнения `CHECK` и триггера, журнал вызовов.

## Лабораторная работа № 3. Построчная изоляция данных с RLS

**Цель:** реализовать изоляцию данных между организациями, филиалами, проектами или группами с помощью Row-Level Security.

### 1. Сегментация

- Выбрать ось изоляции `SEG`.
- Добавить `segment_id` в ключевые таблицы `app.*`.
- Создать внешний ключ на `ref.segment`.
- Создать индексы по `segment_id` и прикладным фильтрам.

### 2. RLS и политики

- Включить `ENABLE ROW LEVEL SECURITY` и `FORCE ROW LEVEL SECURITY`.
- Создать политики для `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
- Идентифицировать субъект через роль сеанса и проверенный контекст.
- Для `INSERT` и `UPDATE` применить `WITH CHECK`.
- Предусмотреть серверное сопоставление login-роли с сегментом; не доверять произвольному значению пользовательского GUC.

### 3. Передача контекста

- Создать `SECURITY DEFINER`-функцию `set_session_ctx(segment_id, actor_id)`.
- Проверять принадлежность роли сегменту и субъекту.
- Устанавливать транзакционный контекст через `set_config(..., true)` — эквивалент `SET LOCAL`.

### 4. Тесты

Подготовить не менее восьми случаев:

- чтение чужих строк;
- вставка и обновление с чужим `segment_id`;
- корректные операции в своём сегменте;
- успешный и неуспешный вызов `set_session_ctx()`;
- удаление своей и чужой строки;
- проверка роли аудитора.

### 5. Аудиторский доступ

- Разрешить членам роли `auditor` видеть строки всех сегментов политикой RLS.
- Не выдавать `BYPASSRLS`, если цель работы — продемонстрировать управляемое исключение внутри политик.

**В отчёт:** ось сегментации, функции контекста, SQL политик, тесты изоляции и проверка аудитора.

## Лабораторная работа № 4. Безопасные представления, аудит и производительность

**Цель:** обеспечить безопасный доступ через представления, организовать аудит изменений и исследовать накладные расходы RLS.

### 1. Представления

- Создать обновляемое представление с `WITH CHECK OPTION` для рабочего набора полей.
- Создать агрегатное представление с `security_barrier`.
- Согласовать работу представлений с RLS с помощью `security_invoker`, если политики должны вычисляться для вызывающей роли.

### 2. История изменений

- Добавить `AFTER UPDATE OR DELETE` триггеры к 2–3 критичным таблицам.
- Записывать пользователя, время, операцию, ключ и образы `OLD`/`NEW` в `audit.row_change_log`.
- Маскировать или хэшировать PII и секреты.

### 3. Тесты

- Попытка обойти `WITH CHECK OPTION`.
- Попытка извлечь детализацию из агрегатного представления.
- Проверка журнала после изменения строки.
- Попытка удалить строку другого сегмента.

### 4. Анализ производительности

- Выполнить `EXPLAIN (ANALYZE, BUFFERS)` для 2–3 типовых запросов до и после RLS.
- Подобрать индексы под выражения политик, например `(segment_id, status)`.
- Зафиксировать время, план и количество обработанных буферов.

### 5. Архивирование

- Создать `backup_audit_logs(days_interval integer)`.
- Атомарно переносить старые строки из `audit.row_change_log` в `audit.row_change_log_archive`.
- Проверить ручной запуск и результат.

**В отчёт:** определения представлений, триггеры аудита, тесты, планы запросов, сравнение показателей и архивирование.

## Расчётно-графическое задание. Модель безопасности и JIT-доступ

**Формат:** ориентировочно 50 страниц, диаграммы, SQL-сценарии и конфигурационные материалы.

### Система временных привилегий

Реализовать функцию:

```sql
request_temp_privilege(operation_name text, duration_min integer)
```

Функция должна:

- проверять, разрешена ли операция членам вызывающей роли;
- ограничивать максимальную длительность доступа;
- записывать запрос в `audit.temp_access_log`;
- создавать серверную запись временного допуска и устанавливать сеансовый маркер;
- обеспечивать проверку допуска при каждой чувствительной операции;
- автоматически отклонять операцию после `expires_at`;
- не предоставлять вызывающему пользователю прямого `DELETE` или иных расширенных прав.

Проверить последовательность: запрос допуска → успешная операция → истечение TTL → отклонение повторной операции.

### Содержание отчёта РГЗ

- предметная область и роли;
- ER-диаграмма;
- матрица классификации;
- DDL схем `app`, `ref`, `audit`, `stg`;
- ограничения и тестовые данные;
- ролевая модель и `DEFAULT PRIVILEGES`;
- запрет `PUBLIC`;
- логирование подключений;
- 2–3 безопасные `SECURITY DEFINER`-функции;
- журнал вызовов;
- сравнение `CHECK` и триггера;
- RLS, контекст сеанса и аудиторская политика;
- обновляемое и агрегатное представления;
- аудит изменений с маскированием;
- анализ производительности;
- архивирование логов;
- система JIT-доступа с TTL.

### Графические материалы

- ER-диаграмма;
- диаграмма ролей и полномочий;
- схема вычисления RLS-контекста;
- схема проверки временного допуска.

### Критерии согласованности

- во всех частях используются одни схемы и роли;
- `segment_id` и `actor_id` интерпретируются одинаково;
- RLS не основывается только на изменяемом пользователем GUC;
- владельцы `SECURITY DEFINER`-функций не имеют `BYPASSRLS`;
- аудит не сохраняет открытые пароли, токены и PII;
- все объекты разворачиваются воспроизводимым сценарием;
- положительные и отрицательные проверки дают документированный результат.

## Важные технические уточнения к заданию

1. **Login event trigger существует в PostgreSQL 18.** Это специальное событие `login`, а не обычный DML-триггер. Создать event trigger может только суперпользователь. В функции необходимо проверять `pg_is_in_recovery()`, иначе запись на standby-сервере может сорвать подключение.
2. **`SECURITY DEFINER` не равен полному административному доступу.** Функция получает права владельца, но безопасный вариант требует фиксированного `search_path`, квалифицированных имён, отзыва `EXECUTE` у `PUBLIC` и минимально привилегированного владельца.
3. **Неуспешный вызов нельзя надёжно записать в ту же БД, если после записи повторно выбросить исключение.** Вся транзакция откатится вместе с журналом. В руководстве ожидаемые ошибки возвращаются как структурированный результат; для аварийных исключений дополнительно применим серверный лог или внешняя система аудита.
4. **RLS обычно скрывает чужую строку как отсутствующую.** Поэтому чужой `DELETE` часто завершается как `DELETE 0`, а не явной ошибкой. `WITH CHECK` при чужом `INSERT`/`UPDATE` выдаёт ошибку политики.
5. **Пользовательский GUC не является доказательством полномочия.** Пользователь может попытаться изменить `app.segment_id` или `app.temp_privilege_until`. Значение должно проверяться по защищённой серверной таблице.
6. **`SET LOCAL` живёт только до конца транзакции.** После `COMMIT` или `ROLLBACK` контекст исчезает. Поэтому `set_session_ctx()` вызывается внутри явного `BEGIN`.
7. **Роль аудитора не должна быть PostgreSQL-superuser.** В работе «режим суперпользователя для auditor» означает управляемый полный обзор прикладных строк через политику, но не атрибут `SUPERUSER` и не `BYPASSRLS`.
